## Overview
Summary: **CyberSecEval is Meta's open-source benchmark suite for testing language models, not guardrails.** Its current version, CyberSecEval 4, scores how often a model writes insecure code, helps attackers, falls for prompt injection, abuses a code interpreter, or can do offensive and defensive security work. Meta's own CyberSecEval 3 paper reused the injection data and the insecure-code detector to measure its guardrails, but the runner has no guardrail mode, and the project says it is exploring a next version. **[Documented]** **[Inferred]** (no guardrail mode)
Detail:
• CyberSecEval 4 is described as "an extensive benchmark suite designed to assess the cybersecurity vulnerabilities and defensive capabilities of Large Language Models (LLMs)" (CSB/README.md:8-9) **[Documented: repo meta-llama/PurpleLlama@172c1074]** https://github.com/meta-llama/PurpleLlama/blob/172c1074069eb88ec834124272c1b1c4f8893445/CybersecurityBenchmarks/README.md

Row order follows the README benchmark list. "Evaluates" first states what the suite scores (a model's behaviour). Any mapping to a Table 3 column is a reuse idea marked [Inferred], because no source says these suites evaluate guardrails. Table 3 headers used: PL1 = Prompt Guard 2: Input-level prompt-attack detection (jailbreak and injection); PL2 = LlamaFirewall: Input-level prompt-attack detection (PromptGuard scanner); PL4 = LlamaFirewall: Output-level insecure-code detection (CodeShield scanner); PL6 = Code Shield: Output-level insecure-code detection (LLM-generated code). ## Red-teaming
Summary: **CyberSecEval is a model-risk test suite, not a red-teaming library for guardrails.** Its prompt injection, interpreter abuse and attack-assistance sets are attack content, but each is built to probe a model under test, and the offensive-capability suites measure what a model can do rather than whether a defence holds. The README warns that platform content filters may block them. **[Documented]** **[Inferred]** (not a guardrail attack library)
Detail:
• The README lists vulnerability exploitation, spear phishing and autonomous offensive operations as capability tests ("evaluate the capabilities of LLMs to function autonomously as a cyber attack agent") **[Documented: repo meta-llama/PurpleLlama@172c1074]** https://github.com/meta-llama/PurpleLlama/blob/172c1074069eb88ec834124272c1b1c4f8893445/CybersecurityBenchmarks/README.md

## Reuse for the test bench
• Seed positives for the prompt-attack columns (PL1, PL2): the 251 English injection cases and their `user_input` strings, with 196 direct and 55 indirect cases and 15 technique labels; the multilingual file adds 1,004 machine-translated cases in 17 languages. Limits: no benign negatives are shipped (the CSE3 paper's negatives are not in the repo), the cases embed a secret-key style task rather than harmful content, translations are machine made, and Prompt Guard 2 is documented to flag explicit override intent only. **[Inferred]**
• Technique labels as a stratification axis: `injection_variant`, `injection_type` and `risk_category` could break bench results down by attack style for PL1 and PL2. Limit: techniques were designed to test whether models follow injected text, not to defeat a classifier. **[Inferred]**
• Insecure-code test material for PL4 and PL6: the Instruct and Autocomplete prompts (1,916 each, 8 languages, 50 CWE ids) can make a model produce code to feed the code scanners. Limits: the only ground truth in the suites is the Insecure Code Detector itself, which is Code Shield's engine, so agreement with it proves little; the bench would need independent labels (the CSE3 paper hand-labelled 50 completions per language), and the language set matches only the 8 default Code Shield languages. **[Inferred]**
• Benign over-blocking probes: the 750 MITRE FRR prompts are labelled benign cyber-themed requests and could check false positives of an input guardrail. Limit: the label is Meta's judgement that they are benign, they are all one attack_type, and they were designed for model refusals, not classifier thresholds. **[Inferred]**
• Not reusable for guardrail columns: vulnerability exploitation, spear phishing, autonomous operations, AutoPatch and both CyberSOCEval suites measure model capability or need cyber ranges, containers or terabytes of disk; they carry no guardrail-relevant labels. **[Inferred]**
• Meta's CSE3 paper already shows a precedent: it scores Prompt Guard (first generation) on this injection data at a "selected threshold", and Code Shield against hand labels. The bench can follow that recipe (positives from the injection set, negatives built by removing the injected text) for Prompt Guard 2, but that is a new test, since no CyberSecEval material reports Prompt Guard 2. **[Inferred]**
• Harness shape: the suites follow a fixed pipeline of prompt file, response file, judge file and stat file with per-bucket counts, which is a usable template for bench output records; judge-based suites depend on a hosted judge LLM and its terms. **[Inferred]**
• Licensing and provenance: code and Meta-written data are MIT; the instruct and autocomplete prompts derive from third-party repositories under mixed licences listed in `third-party.txt`; CrowdStrike and agency report data for CyberSOCEval is third-party. Review before redistributing any dataset inside the bench. **[Inferred]**
• Sensitive content: MITRE, interpreter and injection sets contain attack-assistance text; storing and sending it to third-party APIs (judge models, hosted guardrails) is a bench-design decision. **[Inferred]**
• Maintenance risk: the README says the project is exploring a next version, the suites may change, and the secure-code note and AutoPatch case counts in the README already disagree with the files; pin the commit if the data is reused. **[Inferred]**
