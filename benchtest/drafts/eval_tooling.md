## Topic: NeMo Guardrails built-in evaluation tooling (draft, reuse assessment for the test bench)

Version scope: NeMo Guardrails v0.24.1 (tag `v0.24.1`). Develop branch differences are listed separately at the end of Overview.

## Overview
Summary: **NeMo ships two evaluation toolkits that share one command group, plus a separate performance benchmark folder.** The older toolkit scores four individual checks (dialog intent matching, self-check moderation, self-check fact-checking and a self-consistency hallucination check) against small sample datasets. The newer toolkit runs a developer-written set of policies and conversations through a whole guardrails configuration and uses a language model as the judge of compliance, and it also records call counts, token counts and latency. The evaluation runners instantiate the classic engine class by name and the toolkit never mentions the newer engine; a documented environment switch could re-point that name at the newer engine, but that path is untested here and would probably fail. NVIDIA's published numbers cover the self-check prompts, a Llama Guard comparison, AlignScore, dialog intent accuracy, a garak scan and two perplexity heuristics; most model-based results are dated 2023 to early 2024 and use older models, while the garak scan, the heuristics and the language-detection figures are undated. **[Documented]** **[Inferred]** (engine sentence)
Detail:
• Two toolkits plus a benchmark folder exist in the repo **[Documented: repo v0.24.1]**
  – per-rail tasks `topical`, `moderation`, `hallucination`, `fact-checking` (package `nemoguardrails/evaluate/`). The docs and READMEs write them as `nemoguardrails evaluate ...` **[Documented]**; in the v0.24.1 CLI code they are reachable only as `nemoguardrails eval rail topical|moderation|fact-checking|hallucination` **[Documented: repo v0.24.1]** (code read, not run). In this draft, `evaluate ...` is the legacy name from the docs, and `eval rail ...` is the actual command.
  – `nemoguardrails eval ...` (package `nemoguardrails/eval/`): policy-based workflow with subcommands `run`, `check-compliance`, `ui`, and `rail` (which mounts the per-rail tasks)
  – `benchmark/`: capacity and latency testing of a server (AIPerf sweeps, Locust load tests, mock LLM server) plus an embedding-index micro-benchmark; none evaluates a rail's accuracy
• The evaluation docs say engines that are not OpenAI-compatible (vertexai, anthropic, cohere, azure, huggingface_pipeline, trt_llm and others) need the LangChain framework switched on with `NEMOGUARDRAILS_LLM_FRAMEWORK=langchain` plus the matching `langchain-*` package **[Documented: repo v0.24.1]** https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/docs/evaluation/evaluate-guardrails.mdx
• The tools need the `eval` extra (`nemoguardrails[eval]`: tqdm, streamlit, pandas, numpy) **[Documented: repo v0.24.1]** https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/pyproject.toml
• Not evaluation tooling: `tests/eval/`, `tests/evaluate/` (unit tests), `tests/test_perf_1.py` (skipped manual throughput script) and `nemoguardrails/testing/` (contents not inspected; treated as test code) **[Documented: repo v0.24.1]**
  – sources: https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/cli/__init__.py , https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/eval/cli.py , https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/evaluate/cli/evaluate.py , https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/benchmark/README.md
• NVIDIA's own docs say the per-rail tools "test the performance of each type of rail individually" and that results are preliminary **[Documented]** https://docs.nvidia.com/nemo/guardrails/evaluation/evaluate-guardrails (source file https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/docs/evaluation/evaluate-guardrails.mdx)
• The old per-rail tasks do not call the NeMo rail pipeline for moderation, fact-checking and hallucination; they render the self-check prompt and call the LLM directly, so they test the prompt-based self-check variants only, not NemoGuard, Llama Guard, Presidio, GLiNER, jailbreak heuristics or any other rail **[Documented: repo v0.24.1]** https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/evaluate/evaluate_moderation.py , https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/evaluate/evaluate_factcheck.py , https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/evaluate/evaluate_hallucination.py
• The policy-based `eval run` is the only tool that exercises a full configuration end to end (any rail combination), through `LLMRails.generate_async` **[Documented: repo v0.24.1]** https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/eval/eval.py
• Its stated metrics are compliance rate, resource usage (LLM calls, tokens, actions) and latency; precision, recall and F1 are explicitly not computed ("you need to compute these with other tools") **[Documented]** https://docs.nvidia.com/nemo/guardrails/evaluation/evaluation-methodology (source https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/docs/evaluation/evaluation-methodology.mdx)
• Dataset files bundled in the repo are mostly tiny placeholders (1 to 15 items); the real datasets must be downloaded **[Documented: repo v0.24.1]** (see Datasets)
• Licence of the code: Apache-2.0 (SPDX header in every inspected source file; `LICENSE-Apache-2.0.txt` at repo root) **[Documented: repo v0.24.1]** https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/eval/cli.py
• Develop branch differences: none found. The four files under `docs/evaluation/` and the files under `nemoguardrails/eval/` have byte sizes identical on `develop` and on `v0.24.1`; content was not diffed line by line **[Documented: develop branch]** **[To be verified]** https://github.com/NVIDIA-NeMo/Guardrails/tree/develop/docs/evaluation , https://github.com/NVIDIA-NeMo/Guardrails/tree/develop/nemoguardrails/eval

## Red-teaming
Summary: **Red-teaming is handled by pointing the open-source garak scanner at a guardrails configuration.** The evaluation docs include a vulnerability-scanning page that scanned a sample employee-handbook bot in four stages of protection and reports protection rates per attack family. Garak is an open-source scanner hosted in NVIDIA's GitHub organisation (Apache-2.0), and it contains generators that load a configuration directly or call a running guardrails server. **[Documented]**
Detail:
• The docs page describes garak as "an open-source tool for scanning against the most common LLM vulnerabilities" and compares it with nmap; the page links to https://github.com/NVIDIA/garak/ and does not state who owns it **[Documented]** https://docs.nvidia.com/nemo/guardrails/evaluation/llm-vulnerability-scanning (source https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/docs/evaluation/llm-vulnerability-scanning.mdx)
• Garak lives in the `NVIDIA` GitHub organisation, is Apache-2.0, and its README gives an NVIDIA contact address; latest release v0.17.0, published 2026-09-09 **[Documented]** https://github.com/NVIDIA/garak , https://github.com/NVIDIA/garak/releases/tag/v0.17.0 . Treated as NVIDIA-hosted (official); whether it is an officially supported NeMo Guardrails component is not stated **[To be verified]**
• Garak has a built-in `NeMoGuardrails` generator (loads `RailsConfig.from_path(name)` then `LLMRails`, calls `generate(messages=...)`, returns one string per call, no multiple generations) and a `NeMoGuardrailsServer` generator (OpenAI-compatible, URI default `http://localhost:8000/v1/`, optional `config_ids`) **[Documented]** https://github.com/NVIDIA/garak/blob/main/garak/generators/guardrails.py (main branch at time of reading; not pinned to a release)
• Garak probe families in its README include dan, encoding, goodside, promptinject, gcg, leakreplay, malwaregen, lmrc, realtoxicityprompts, snowball, xss, packagehallucination, donotanswer and others; default generations per prompt is 10 per its README **[Documented]** https://github.com/NVIDIA/garak/blob/main/README.md
• The scan in the NeMo docs used four configurations (`bare_llm`, `with_gi`, `with_gi_dr`, `with_gi_dr_mo`) with HTML reports stored under `docs/_static/html/` **[Documented]**; the docs admit it did not measure false positives on legitimate requests **[Documented]**
• The docs name no jailbreak red-team dataset and no attack-generation tool inside NeMo itself; the only attack content inside the repo's evaluation folder is the Anthropic red-team prompts used for moderation **[Documented: repo v0.24.1]**
• No other scanner integration (PyRIT, promptfoo) was found in the evaluation docs **[Not disclosed]**

## Engine coverage
Summary: **The built-in evaluation runners are written for the classic runtime.** They instantiate the classic engine class by name and the toolkit makes no mention of the newer engine. A documented environment switch re-points that class name at the engine-selecting wrapper, so the runners could receive the newer engine for supported configurations; that path is untested here, and the run would probably fail because the policy runner asks for Colang-only log fields that the newer engine rejects. They send plain text or role-tagged messages one request at a time, with no streaming and no tool-call support. **[Documented: repo v0.24.1]** **[Inferred]** (failure prediction) **[To be verified]** (overall IORails status)
Detail:
• `eval run` and the four per-rail tasks import the name `LLMRails` from `nemoguardrails` **[Documented: repo v0.24.1]**
• `nemoguardrails/__init__.py` sets `LLMRails = Guardrails` (the engine-selecting facade) when `NEMO_GUARDRAILS_IORAILS_ENGINE=1` **[Documented: repo v0.24.1]** https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/__init__.py
• `eval check-compliance` and `eval ui` do not build rails at all **[Documented: repo v0.24.1]** https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/eval/check.py
• IORails raises `NotImplementedError` for the `log.internal_events` option, and `eval run` requests `{"log": {"activated_rails": True, "internal_events": True}}`, so `eval run` would probably fail under IORails; IORails does synthesize `activated_rails`, `llm_calls` and `stats` **[Documented: repo v0.24.1]** (engine page) **[Inferred]** (failure prediction) https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/docs/reference/engine-feature-support.mdx
• Overall status of the tools on IORails: not tested **[To be verified]**
• Original instantiation sites (kept for reference): `eval.py`, `evaluate_moderation.py` **[Documented: repo v0.24.1]** https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/eval/eval.py , https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/evaluate/evaluate_moderation.py
• Search for `IORails` in `nemoguardrails/eval` returned no hits on the default branch; the evaluation docs never mention it; the engine feature page does not mention evaluation tooling **[Documented: develop branch]** https://docs.nvidia.com/nemo/guardrails/reference/engine-feature-support
• `topical` is by construction LLMRails only because dialog rails need the Colang runtime (dialog rails not supported in IORails) **[Documented]** https://docs.nvidia.com/nemo/guardrails/reference/engine-feature-support (as summarised in `drafts/two_level_v2.md`, Column D)
• Streaming: `eval run` uses `generate_async` with full responses; no streaming option **[Documented: repo v0.24.1]**. The runtime does support output-rail streaming on both engines, but nothing in the evaluation code measures it **[Documented]**

• Whether tool-role messages pass through `messages` inputs untouched is untested (inputs are `Union[str, dict]` and `messages` is passed through unchanged) **[Inferred]**
• Using the garak server generator against a running server could reach IORails if the server selects that engine **[Inferred]** **[To be verified]**

## Reuse for the test bench
• Policy-and-interaction data model as a harness shape: policies with natural-language rules, interaction sets with expected behaviour (refusal, similar message, generic), include/exclude policy lists, tags, and multi-turn message inputs map well to Table 3 columns such as jailbreak, topic control, content safety and dialog. Reusing the schema (not the code) would give the bench per-policy compliance rates. Limits: LLMRails-only runner, no tool or streaming fields, English examples. **[Inferred]**
• Run record format as a metric template: per-interaction output, activated rails, LLM-call counts, prompt/completion token counts and per-action latency are exactly the "LLM calls" and latency columns the bench wants; the span-trace aggregation in `eval/eval.py` and `eval/utils.py` is plain Python over `GenerationLog`. Limits: IORails supplies activated rails, LLM calls and stats, which is what the span aggregation uses, but it rejects the `internal_events` log option that `eval run` requests, so the runner would need that option removed. **[Inferred]**
• LLM-judge prompt and discipline from `check-compliance`: temperature 0, strict `Reason:/Compliance:` parse, per-policy custom prompt, "n/a" handling, plus the advice to re-run the judge and manually annotate inconsistencies. Reusable as a template if the bench needs a judge. Limits: judge dependence, answer-format brittleness (invalid replies are silently ignored), and it measures reply-level compliance rather than which rail fired. **[Inferred]**
• The moderation task scores by substring "yes"/"no" in the model answer, the fact-check task by substring, and the hallucination task flags a sample when "no" appears anywhere in the judge text (so "not" and "know" also match) and has no ground truth; all three bypass the rail pipeline **[Documented: repo v0.24.1]**. The bench should therefore not rely on these tasks for baselines and should compute **[Inferred]** its own confusion matrix (precision, recall, F1, false positive rate) from block/allow outcomes of the real rails. **[Inferred]**
• Datasets worth reusing as seed data: Anthropic red-team-attempts and helpful-base for input harmful vs benign prompts (MIT, per the HF card; offensive content; first-turn prompts only; English; old, from 2022; prompts are not labelled by category, only a harmfulness rating); MS MARCO positives plus the documented LLM-adversary recipe for grounded fact-checking negatives (English; HF card does not state a licence; synthetic negatives depend on the generating model); OpenAI Moderation test set (not in repo, licence not checked) and ToxicChat as the larger labelled input sets NVIDIA used for the Llama Guard comparison; ToxicChat is CC BY-NC 4.0, non-commercial only, and its current card (7.33% toxic) differs from NeMo's 730 (7.2%). **[Inferred]**
• Dialog column: chit-chat and banking intent datasets plus NeMo's conversion scripts give ready dialog-rail test sets with canonical forms and known intents; bundled apps already exist. Limits: needs the original dataset downloads, banking is CC-BY-4.0 (attribution required), English only, only tests the Colang 1.0 intent engine and LLMRails. **[Inferred]**
• Hallucination column: the 15 false-premise questions are a usable smoke test only; no labels and no negatives. **[Inferred]**
• Red-teaming: garak plus its guardrails generators can supply attack probes (dan, encoding, goodside, promptinject, gcg, leakreplay, malwaregen) for jailbreak and injection columns, and gives a protection-rate view comparable to NVIDIA's table. Limits: does not measure false positives on legitimate users, probe sets drift with garak versions, some detectors are model-based, and the generator path is LLMRails or server only. **[Inferred]**
• Performance: `benchmark/` (AIPerf concurrency sweeps with mock LLMs) can be reused for the latency and overhead columns without GPUs; it measures capacity of a server, not rail accuracy. **[Inferred]**
• Do not reuse NVIDIA's published numbers as bench baselines: all use retired models (text-davinci-003, gpt-3.5 family, gemini-1.0-pro), prompts are the simple self-check prompts, samples are small (100 prompts, 100 triples), and none cover the Table 3 rails other than self-check moderation, fact-checking, hallucination, dialog and jailbreak heuristics. **[Inferred]**
• Gaps the bench must fill itself, since NeMo provides no evaluation for them: PII in/out, retrieval, regex, injection (beyond garak), context bloat, tool-call validation, tool-result validation, execution rails, NemoGuard model accuracy, streaming leak testing, and IORails. **[Inferred]**
