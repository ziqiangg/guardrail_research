## Top 5 decision-relevant findings

1. Tool rails (a3): the built-in `tool call validation` / `tool result validation` exist only on IORails (Colang 1.0, OpenAI wire format). LLMRails runs the `rails.tool_output` / `rails.tool_input` sections but only with user-authored Colang flows. The Engine Feature and Rail Engine Support pages overstate LLMRails support for the named built-ins. Bench: use IORails for built-ins; write custom Colang subflows for LLMRails.
2. `tool_safety_check` and per-tool regex (a4, a5) are develop-only; absent from v0.24.1, the latest release. Mark out of scope for a v0.24.1 bench.
3. `rails.execution` with `check tool input/output` (R8) is a docs example with no config field and no flow in v0.24.1. Do not use it. Real execution controls are `rails.actions.instant_actions` and custom actions (LLMRails only).
4. Fact-check/hallucination rails (`self check facts`, `self check hallucination`, alignscore, patronus) are LLMRails only, and so is the heuristics jailbreak flow (a2). A config using them silently routes to LLMRails unless `require_iorails=True`. Same silent fallback for any mistyped tool flow (a44); set `require_iorails=True` in the harness.
5. `enable_rails_exceptions` (a13): honoured by jailbreak flows, not by sensitive-data flows (they emit a canned refusal), and ignored on IORails (fixed refusal / `guardrails_violation` payload). Assertions must be engine- and rail-specific.
