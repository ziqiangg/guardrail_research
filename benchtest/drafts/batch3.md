# NeMo Guardrails research table: Batch 3 draft (pinned to docs latest + GitHub v0.24.1)

## Column K: NeMo Guardrails: Tool-call validation

- **R1:** **Tool-call validation (output side).** Checks each tool call the model emits against the tools the application declared, before the call reaches the application. It is a local structural check with no LLM call. **[Documented]**
- **R2:** **Unknown tools, malformed arguments and invalid tool schemas.** Addresses calls to a tool outside the allowlist, arguments that violate the tool's JSON Schema, arguments supplied to a no-parameter tool, and a declared schema that is itself invalid. **[Documented]** It does not judge whether an allowed call is harmful. **[Inferred]**
- **R3:** **Model response, after the main LLM.** Flow `tool call validation` under `rails.tool_output.flows`. A response with only tool calls skips the text output rails. A block returns "I'm sorry, I can't respond to that."; streaming returns a `guardrails_violation` payload; a provider failure returns "I'm sorry, an internal error has occurred." The rail does not execute tools. **[Documented]**
- **R4:** **Structural allowlist and JSON Schema check.** Supports only the OpenAI Chat Completions format (`openai` and `nim` engines). **[Documented]** Engine support conflicts in the docs. The tool-calling page says these rails "run only on the IORails engine… not available on the default `LLMRails` engine" and need Colang 1.0. **[Documented]** The rail-engine-support and engine-feature-support pages mark both tool rails as supported on LLMRails and IORails. **[Documented]** A misdirected, unknown or duplicated flow name silently falls back to LLMRails with no tool rail. **[Documented]** An LLM-based `tool_safety_check` rail exists on the develop branch only (not in v0.24.1; allow/block/moderate; IORails). **[Not disclosed in v0.24.1 docs] [To be verified]** Per-tool regex checks on tool-call arguments appear in develop-branch docs only (not in v0.24.1). **[To be verified: future release]** No third-party backends are documented for this function. **[To be verified]**
- **R5:** **Allow or block outcome.** A block gives the fixed refusal text (non-streaming) or a `guardrails_violation` error payload (streaming). Block reasons are strings such as "tool call 'x' is not an allowed tool". A provider outage gives an internal-error message instead. **[Documented]** The streamed tool-call chunk is suppressed after a block. **[Documented]**
- **R6:** **Declared tools plus the model's tool calls.** Needs tool definitions in `options.llm_params.tools` or `models[].parameters.tools`, and a model that emits tool calls. Hosted tools identified only by `type` are allowlisted by type and their arguments are not schema-validated. **[Documented]**
- **R7:** **Minimum setup:** harness sending requests with declared tools, a model or scripted responses that emit valid, unknown-name, bad-argument and no-parameter-with-arguments calls, an IORails config with `tool call validation`, and a recorder for refusals and payloads. No tool execution is needed. **[Inferred from the documented rail position]**
- **R8:** Verify which engine runs tool rails on v0.24.1 (the docs conflict), whether the `tool_safety_check` rail and per-tool regex checks reach a release, behaviour for non-OpenAI wire formats, tool-call arguments seen by plain output rails, silent fallback when a flow name is mistyped, whether JSON Schema dialect variants validate

## Column L: NeMo Guardrails: Tool-result validation

- **R1:** **Tool-result validation (input side).** Checks `role: tool` messages in the request before the model sees them. It is a local structural check with no LLM call. **[Documented]**
- **R2:** **Malformed or inconsistent tool results.** Addresses a missing or unlinked `tool_call_id`, duplicate IDs within the turn, a name that differs from the linked call, and content that is not a string or content-block list. **[Documented]** It is not a content-safety or prompt-injection check on result text. **[Documented]**
- **R3:** **Request input, before the main model.** Flow `tool result validation` under `rails.tool_input.flows`, run alongside the input rails. Refusal and error behaviour matches the tool-call rail. Plain input/output rails see only the `content` field, so tool-call arguments are not inspected by them and tool results bypass input rails. **[Documented]**
- **R4:** **Structural linkage check only.** It does not enforce a response schema or run a content-safety check, and consistency is checked within one request only, with no cross-turn provenance. **[Documented]** Engine support conflicts in the docs. The tool-calling page says IORails only (not on `LLMRails`, Colang 1.0 needed). **[Documented]** The rail-engine-support and engine-feature-support pages mark it supported on both engines. **[Documented]** An LLM-based `tool_safety_check` rail (develop branch only, not in v0.24.1; judges the tool result; allow/block/moderate; IORails) exists in source and is undocumented in v0.24.1. **[Not disclosed in v0.24.1 docs] [To be verified]** Per-tool regex checks on tool results appear in develop-branch docs only (not in v0.24.1). **[To be verified: future release]** No third-party backends are documented. **[To be verified]**
- **R5:** **Allow or block outcome.** A block gives "I'm sorry, I can't respond to that." (non-streaming) or a `guardrails_violation` payload (streaming). A provider failure gives "I'm sorry, an internal error has occurred." **[Documented]**
- **R6:** **Conversation history with tool messages.** Needs the assistant turn containing the tool calls and one `role: tool` message per `tool_call_id`, resent on each request. Declared tools are needed for name checks. **[Documented]**
- **R7:** **Minimum setup:** harness sending conversations with tool messages (valid, missing id, duplicate id, wrong name, non-string content), an IORails config with `tool result validation`, a stub main LLM, and a recorder. No real tool execution is needed. **[Inferred from the documented rail position]**
- **R8:** Verify which engine runs tool rails on v0.24.1 (the docs conflict), whether `tool_safety_check` and per-tool regex checks reach a release, no content check on tool results (injection via results unaddressed), cross-turn provenance, non-OpenAI formats, redundant-flow fallback to LLMRails

## Column M: NeMo Guardrails: Grounded fact-checking (output)

- **R1:** **Grounded fact-checking (output).** Checks whether the bot reply is supported by the retrieved evidence (`relevant_chunks`) before it reaches the user. **[Documented]**
- **R2:** **Unsupported claims in RAG answers.** Addresses replies that contradict or go beyond the knowledge-base chunks. It does not help without retrieved evidence. **[Documented]**
- **R3:** **Bot response, after the main model.** Output flows `self check facts`, `alignscore check facts`, `patronus lynx check output hallucination`. `self check facts` only runs when `$check_facts == True`. **[Documented]**
- **R4:** **Entailment judgement against evidence.** `self check facts` has the LLM score support from 0 to 1 (the docs example blocks below 0.5; empty or truncated output fails closed with 0.0). `alignscore check facts` calls an AlignScore server at `rails.config.fact_checking.parameters.endpoint`; Patronus Lynx is a hallucination model (8B and 70B). **[Documented]** All run on LLMRails only; IORails does not support them because they read `relevant_chunks`. Per the v0.24.1 support matrix this covers self check facts, alignscore, autoalign groundedness, fiddler faithfulness, patronus api and patronus lynx. **[Documented]** Optional third-party backends: Patronus API (paid / non-OSS service), Fiddler bot faithfulness (paid / non-OSS service), AutoAlign groundedness and factcheck (paid / non-OSS service), Cleanlab trustworthiness (paid / non-OSS service; runs on IORails), AlignScore (open-source, self-hosted), Patronus Lynx (open-weight model, licensing to be verified) **[To be verified]**
- **R5:** **Score and block decision.** `self check facts` returns a 0 to 1 score and the flow blocks below a threshold. Other backends return their own pass/fail or scores. **[Documented]** Exact output shape per vendor is unconfirmed. **[To be verified]**
- **R6:** **Reply plus retrieved chunks.** Needs a knowledge base or `relevant_chunks` set in context, the `check_facts` flag set, and for self-check a `self_check_facts` prompt and main LLM. AlignScore needs a running server; vendors need accounts or keys. **[Documented]**
- **R7:** **Minimum setup:** harness, a small knowledge base or injected `relevant_chunks`, supported and unsupported answer pairs, a LLMRails config with the chosen flow, a judge LLM or AlignScore server, and a recorder. **[Inferred from the documented rail position]**
- **R8:** Thresholds for non-LLM backends, verify the IORails exclusion list on v0.24.1 (matrix read from the v0.24.1 tag), vendor licensing and cost, AlignScore model licence, behaviour with long or multiple chunks, false positive rates, how `$check_facts` is set in practice
- **R9:** https://docs.nvidia.com/nemo/guardrails/configure-guardrails/guardrail-catalog/fact-checking ; https://docs.nvidia.com/nemo/guardrails/reference/rail-engine-support ; https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/docs/reference/rail-engine-support.mdx

## Column N: NeMo Guardrails: Self-consistency hallucination detection (output)

- **R1:** **Self-consistency hallucination detection (output).** Samples extra generations and checks whether they agree with the original reply; disagreement suggests a hallucination. No grounding documents are needed. **[Documented]**
- **R2:** **Fabricated facts without retrieval.** Addresses unstable parametric answers. It cannot catch a consistent but wrong answer. **[Inferred]**
- **R3:** **Bot response, after the main model.** Flows `self check hallucination` (blocks) and `hallucination warning` (appends a warning). They run when `$check_hallucination` or `$hallucination_warning` is set. **[Documented]**
- **R4:** **Resampling plus an LLM agreement check.** By default two extra responses at temperature 1.0 are generated, then the LLM judges agreement with the original (a "no" blocks). **[Documented: repo v0.24.1]** The check only supports LLM-based agreement; a BERT-score path is a TODO. **[Documented: repo v0.24.1]** LLMRails only; IORails does not support it because it reads `_last_bot_prompt`. **[Documented]** If every extra generation fails the rail allows the reply. **[Documented: repo v0.24.1]** Supported main-LLM providers are not stated; code makes parallel separate calls rather than an `n` parameter. **[To be verified]** No third-party backends are documented. **[To be verified]**
- **R5:** **Block or warning.** Outcome is allow or block with metadata `is_hallucination`; the warning flow appends text instead of blocking. **[Documented: repo v0.24.1]**
- **R6:** **Bot reply and the prompt that produced it.** Needs the last bot prompt, a main LLM, a `self_check_hallucination` prompt, and the flag set. **[Documented]**
- **R7:** **Minimum setup:** harness, prompts with stable answers and prompts the model tends to invent answers for, a LLMRails config with the flow and flag, a main LLM allowing temperature 1.0, and a recorder. **[Inferred from the documented rail position]**
- **R8:** Which main-LLM providers work (the docs may restrict this; not confirmed), added latency and cost of three-plus LLM calls, accuracy of the agreement judge, fail-open on extra-call failure, how the flags are set, interaction with streaming
- **R9:** https://docs.nvidia.com/nemo/guardrails/configure-guardrails/guardrail-catalog/fact-checking ; https://docs.nvidia.com/nemo/guardrails/reference/rail-engine-support ; https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/library/hallucination/actions.py ; https://github.com/NVIDIA-NeMo/Guardrails/blob/v0.24.1/nemoguardrails/library/hallucination/rail.py

## Reviewer notes

- Engine conflict (K, L): the v0.24.1 repo copies of the tool-calling page and rail-engine-support page contain the same conflict as the live docs. The tool-calling page says IORails only and Colang 1.0; the support page says both engines, adding "Tool rails are not manifest surfaces. IORails registers them separately as local structural and schema validators." Code evidence at v0.24.1: `tool call validation` is implemented in `nemoguardrails/guardrails/actions/tool_call_action.py` (IORails package; docstring "Tool-call safety rail for IORails"), and `nemoguardrails/library/` has no tool-rail directory, so no built-in Colang flow of that name was found. The LLMRails claim may refer to custom Colang tool-output actions (Tools Integration docs). I could not read config.py or llmrails.py (fetch errors), so the conflict is not fully resolved; both statements are kept as [Documented].
- tool_safety_check: the path `nemoguardrails/library/tool_safety_check` does NOT exist at tag v0.24.1 (library listing confirms). It exists on the default branch (develop), with `rail.py` declaring flows `tool safety check output` / `tool safety check input` (TOOL_OUTPUT/TOOL_INPUT, capabilities allow/block/moderate, per-tool config via `per_tool`, optional `argument`). Develop also has a docs page `tool-safety-check.mdx` and an example config, so it is not "undisclosed" in develop docs; it is undocumented only for v0.24.1. Text in K/L R4 reflects this. The live docs site and Context7 were not checked for that page.
- Per-tool regex: follows the coordinator update; v0.24.1 regex/rail.py has only input, output and retrieval surfaces. Develop has `per_tool` examples and tests.
- Fact-checking (M): the IORails exclusion list matches the v0.24.1 rail-engine-support page (read directly): alignscore, autoalign groundedness, fiddler bot faithfulness, self check hallucination, patronus api, patronus lynx, self check facts. Note `autoalign factcheck output` and `cleanlab trustworthiness` are supported on IORails. The "0.5 threshold" and "fail-closed 0.0" came from WebFetch summaries and Context7, not verbatim pages; re-check before citing. Vendor paid status is general knowledge, not from NVIDIA docs.
- Hallucination (N): the actions code at v0.24.1 was read directly (2 extra responses, temperature 1.0, "no" in agreement blocks, fail-open when no extra responses). The docs and Context7 returned no statement limiting providers to OpenAI-style models, so that claim is unconfirmed rather than refuted.
