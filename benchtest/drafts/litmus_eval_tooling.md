## Overview
Summary: **Litmus is a hosted testing service for AI applications, not a guardrail.** It sends curated prompts to an application endpoint before launch and scores the responses, from a web app or CI/CD pipeline. It tests a system and does not defend one at runtime. **[Documented]**
Detail:
• Litmus is "a multi-tenant SaaS service enabling development teams to perform frequent and seamless AI safety and security testing for Generative AI applications", usable "within the CI/CD pipeline and via a Web App" (DOCS Litmus-Overview, read 2026-10-10) **[Documented]**
• The Overview names the goal as a "Testing as a Service" platform for WOG (whole-of-government) application developers, with "baseline assurance that AI applications mitigate risks" (DOCS Litmus-Overview) **[Documented]**
• How a run works, in four steps (DOCS Litmus-Overview, "Breakdown of Automated Safety Testing with Litmus") **[Documented]**
  – 1: the tenant sets up with Litmus and integrates the application CI/CD pipeline, which schedules an automatic trigger
  – 2: "Litmus sends hundreds of curated prompts to the tenant’s application, which then forwards them to the LLM"; the application relays the responses back to Litmus
  – 3: "Litmus performs an automated internal evaluation of these responses and automatically generates a report"
  – 4: Litmus sends the report to the tenant pipeline for storage; tenants can also open it in Litmus "to analyse trends and make comparisons"
• Litmus tests a system and is not a runtime defence: "Litmus tests a system; it does not defend one at runtime." (PB tools/litmus.md line 46); the playbook adds that it "does not evaluate whether your system does its job well" **[Documented: repo govtech-responsibleai/playbook@45908b48]**
• Direction note (R002): Litmus is not an inline guardrail. It sends prompts to a tenant endpoint and judges the application responses, so no Litmus function is labelled Input-level or Output-level in this draft **[Inferred]** (premise: Overview steps 2 and 3 describe prompts going out and responses being scored; the playbook quote above)
• Who may use it: "Litmus is available to public sector teams through AI Guardian" and the web application "signs in with TechPass" (PB tools/litmus.md line 57) **[Documented: repo govtech-responsibleai/playbook@45908b48]**
• Onboarding starts with an interest form: "Fill up the Litmus and Sentinel interest form at https://form.gov.sg/67a2f35fdd4157c04aed3cea" (DOCS Litmus-Getting-Started; the form was not opened, R019) **[Documented]**

## Red-teaming
Summary: **Litmus runs curated prompts; adaptive attack generation is not described.** The playbook calls them curated adversarial prompts, and one test uses variations of the DAN jailbreak. No page mentions mutation, automated attack generation or red-team automation. **[Not disclosed]**
Detail:
• Litmus "sends curated adversarial prompts at your AI system, scores the responses, and returns a report" (PB tools/litmus.md line 9) **[Documented: repo govtech-responsibleai/playbook@45908b48]**
• The docs say "Litmus sends hundreds of curated prompts to the tenant’s application" (DOCS Litmus-Overview) **[Documented]**
• The DoAnythingNow test uses a fixed dataset: "The dataset includes variations of the DAN prompt to assess whether the model adheres to ethical guidelines and refuses to generate harmful or prohibited content" (DOCS Test-Information-Documentation) **[Documented]**
• Automated attack generation, prompt mutation, adaptive or multi-turn red-teaming in Litmus is not described (checked the Litmus Overview, Getting Started, Test Information Documentation, Troubleshooting, the five portal pages, the one-pager and the playbook Litmus page) **[Not disclosed]**
• "Custom scenarios" and "user simulation" exist as feature names only: "Custom workflow and user simulation | Design tailored test cases that simulate real user interactions and end-to-end workflows" (PORTAL features-roadmap, last updated 06 May 2025); how they work is not described **[Documented]**
• The playbook Safety evals page separates the two: "safety testing focuses on common attacks and is kept deliberately generic" while red-teaming "generates novel prompts"; it is general guidance and not Litmus documentation (https://github.com/govtech-responsibleai/playbook/blob/45908b48c0a8b6d3855a154c0e41a12958a99205/website/docs/evaluating-ai-systems/safety.mdx, line 17) **[Documented: repo govtech-responsibleai/playbook@45908b48]**

## Reuse for the test bench
• A possible use of the 14-test list: its categories (Security, Specialised Advice, Undesirable Content, Political Content) and tests (for example Domestic Affairs, Geopolitics, All Other Misconduct "under Singapore law") could be a checklist of Singapore-context safety themes when a bench writes its own prompt sets. Litmus publishes no prompts, so this would be a theme list only. **[Inferred]**
• The six Undesirable Content tests (Hateful, Physical Violence, All Other Misconduct, Self-Harm, Sexual, Insults) have the same names as the six harm categories of the Sentinel LionGuard 2 column on sheet 3; a bench could use them to line up cases across the two products. This is a name overlap, and no page says Litmus uses LionGuard categories. **[Inferred]**

• The playbook's WOG safety taxonomy (12 risk categories, some with levels L1 and L2) could be a possible taxonomy to map bench cases to, with the caveat that no page says Litmus uses it and that the taxonomy has categories the 14 tests lack (for example Graphic Content, Race and Religion). **[Inferred]**
• The endpoint-plus-key contract and a per-test pass or fail result could be a shape for bench records (endpoint, parameters, test, outcome); the docs give no schema, so the fields would be the bench's own. **[Inferred]**
