## Overview
Summary: **Litmus is a hosted testing service for AI applications, not a runtime defence.** It scores an application's responses to curated prompts, from a web app or CI/CD. It is available to public sector teams; a May 2025 portal page labels it proof of concept. **[Documented]**
Detail:
• Litmus is "a multi-tenant SaaS service enabling development teams to perform frequent and seamless AI safety and security testing for Generative AI applications", usable "within the CI/CD pipeline and via a Web App" (DOCS Litmus-Overview, read 2026-10-10) **[Documented]**
• The Overview names the goal as a "Testing as a Service" platform for WOG (whole-of-government) application developers, with "baseline assurance that AI applications mitigate risks" (DOCS Litmus-Overview) **[Documented]**
• How a run works, in four steps (DOCS Litmus-Overview, "Breakdown of Automated Safety Testing with Litmus") **[Documented]**
  – 1: the tenant sets up with Litmus and integrates the application CI/CD pipeline, which schedules an automatic trigger
  – 2: "Litmus sends hundreds of curated prompts to the tenant’s application, which then forwards them to the LLM"; the application relays the responses back to Litmus
  – 3: "Litmus performs an automated internal evaluation of these responses and automatically generates a report"
  – 4: Litmus sends the report to the tenant pipeline for storage; tenants can also open it in Litmus "to analyse trends and make comparisons"
• Litmus tests a system and is not a runtime defence: "Litmus tests a system; it does not defend one at runtime." (PB tools/litmus.md@45908b48:46) **[Documented: repo govtech-responsibleai/playbook@45908b48]**
• The playbook adds that Litmus "does not evaluate whether your system does its job well" (PB tools/litmus.md@45908b48:17) **[Documented: repo govtech-responsibleai/playbook@45908b48]**
• Runs can be triggered "manually from the web application, on a schedule, or from a CI/CD job on each commit or deployment" (PB tools/litmus.md@45908b48:25) **[Documented: repo govtech-responsibleai/playbook@45908b48]**
• Direction: Litmus is not an inline guardrail. It sends prompts to a tenant endpoint and judges the application's responses, so it has no input-level or output-level function **[Inferred]** (premise: Overview steps 2 and 3 describe prompts going out and responses being scored; the playbook sentence "Litmus tests a system; it does not defend one at runtime")
• Who may use it: "Litmus is available to public sector teams through AI Guardian" and the web application "signs in with TechPass" (PB tools/litmus.md@45908b48:57) **[Documented: repo govtech-responsibleai/playbook@45908b48]**

## Red-teaming
Summary: **Litmus runs curated prompts; adaptive attack generation is not described.** The playbook calls them curated adversarial prompts, and one test uses variations of the DAN jailbreak. No page mentions mutation, automated attack generation or red-team automation. **[Not disclosed]**
Detail:
• Litmus "sends curated adversarial prompts at your AI system, scores the responses, and returns a report" (PB tools/litmus.md@45908b48:9) **[Documented: repo govtech-responsibleai/playbook@45908b48]**
• The docs say "Litmus sends hundreds of curated prompts to the tenant’s application" (DOCS Litmus-Overview) **[Documented]**

## Reuse for the test bench
• A possible use of the 14-test list: its categories (Security, Specialised Advice, Undesirable Content, Political Content) and tests (for example Domestic Affairs, Geopolitics, All Other Misconduct "under Singapore law") could be a checklist of Singapore-context safety themes when a bench writes its own prompt sets. Litmus publishes no prompts, so this would be a theme list only. **[Inferred]**
• The six Undesirable Content tests (Hateful, Physical Violence, All Other Misconduct, Self-Harm, Sexual, Insults) have the same names as the six harm categories of the Sentinel LionGuard 2 column on sheet 3; a bench could use them to line up cases across the two products. This is a name overlap, and no page says Litmus uses LionGuard categories. **[Inferred]**
• The Cybersecurity Risks Evaluation test is described as a "mix of benign and malicious inputs"; a bench could follow that design by pairing attack examples with harmless look-alike messages, written by the bench or taken from other sources. Litmus does not publish its messages. **[Inferred]**
• The playbook's WOG safety taxonomy (12 risk categories, some with levels L1 and L2) could be a possible taxonomy to map bench cases to, with the caveat that no page says Litmus uses it and that the taxonomy has categories the 14 tests lack (by name: Graphic Content and Race & Religion; compared by name only). **[Inferred]**
• The endpoint-plus-key contract and a per-test pass or fail result could be a shape for bench records (endpoint, parameters, test, outcome); the docs give no schema, so the fields would be the bench's own. **[Inferred]**
• Suggested design cautions from the playbook pitfalls: test the production path, and read refusal rates beside functional evals, since "a system that refuses every request may score well on refusal-based safety tests" (PB tools/litmus.md@45908b48:53). **[Inferred]**
• Some test descriptions depend on the application (Medical: "unless it is a medical chatbot"; Financial: "unless it is a financial services specific chatbot"), so a bench could record the application's purpose with each case. **[Inferred]**
• Litmus is offered to public sector teams through onboarding, so a bench could treat it as a reference and not as a tool it can run **[Inferred]** (premise: the playbook sentence and Getting Started step 1)
• Sensitive content: bench prompts in the hateful, sexual, self-harm and violence areas are suggested to be kept out of shared logs. **[Inferred]**
• No Litmus test dataset is published, so there is nothing to download or redistribute (checked the docs, the playbook, the sample Action and the GovTech Hugging Face dataset cards named above). **[Not disclosed]**
